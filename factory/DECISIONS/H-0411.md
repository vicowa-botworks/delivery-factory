## H-0411 · A fully approved, clean, green pull is waiting on a human: does the queue merge it itself, queue the merge with GitHub, or keep waiting?

- Question: the supervisor already verifies every fact a merge needs — approving review,
  `mergeable`, `mergeStateStatus=CLEAN`, every check SUCCESS — at the moment of the merge, and
  `factory_merge` then refuses anything that fails the re-read. Since H-0408 an `awaiting_merge`
  row whose checks are only *pending* waits in `checks_pending` with a daily notice, and the
  measured cost of that wait is this session's own queue: #5 and #6 each sat approved and clean
  while their checks ran, and PR #5 sat a further interval after green purely because the
  operator, not the queue, had to act. The operator directive of 27 Nov names the shape: "the
  factory should merge any fully approved PR that is passing CI and has no conflicts ... It
  would even be better for it to enable auto-merge if that is enabled on the repo." But this
  repository has `allow_squash_merge=false` and `allow_rebase_merge=false`, so every merge —
  whenever and whoever starts it — is permanent history, and `AGENTS.md` is explicit that a
  merge the supervisor could make must not be hand-made around it: "a hand merge skips that and
  cannot be undone here". Which merge authority does an unattended loop take?
- Options: the plain direct merge the directive leads with — when a pass re-reads APPROVED,
  CLEAN and all-SUCCESS it merges on the spot — but it fires only at the instant a pass happens
  to run, so a pull that goes green between activations waits up to a full interval with a
  person as the only thing that can end the wait, and it duplicates machinery (re-read,
  journal, closeout) that GitHub already runs as a first-class queue | keep waiting for a
  human, the #1813 status quo — but the directive retires it, and the measured cost is the
  queue above | hand the merge to GitHub's own auto-merge queue (`gh pr merge --auto`) at the
  moment the row is verified APPROVED+CLEAN with checks *pending*, so the server — which sees
  every check-complete event — merges within seconds of green, while every gate stays exactly
  where it is, at enqueue time
- Chose: hand the merge to GitHub's own auto-merge queue (`gh pr merge --auto`) at the moment the row is verified APPROVED+CLEAN with checks *pending*, so the server — which sees every check-complete event — merges within seconds of green, while every gate stays exactly where it is, at enqueue time
- Why: the chosen option depends on the repository enabling auto-merge and moves the merge's
  timing to GitHub's, so the closeout the merge arm performs (journal, closure verification,
  worktree and branch retirement) no longer runs by construction — the sweep below is what pays
  that debt. The gate is what the safety lives in, and the queueing moves nothing about it —
  the
  enqueue re-reads the four facts exactly as `factory_merge` does, so an unapproved or dirty or
  red pull never reaches GitHub's queue at all, and GitHub's queue is strictly more conservative
  than the direct arm: it merges at check-completion only if the pull is *still* approved and
  clean then, a re-verification no shell loop can perform between activations. `--merge` is
  pinned into the call because the repo's own settings decide the shape only when a
  `SQUASH`/`REBASE` method is not named, and naming anything beside `MERGE` against this
  repository is a refusal, not a fallback. The capability is asked of the repository first —
  `.allow_auto_merge` over the same REST shim every read uses — and a repository that does not
  enable it fails closed to the old plain wait, journaling `AUTO-ENQUEUE-REPO-NO`; the option
  the directive calls "even better" must never be assumed. Every enqueue is judged by the
  read-back of `autoMergeRequest`, not by gh's exit status (#1180's rule one remove from the
  merge itself), and stamped once (`pr:<n>.auto-enqueue`) because the queue owes no repeat
  offer. The server writing the merge is the #1180 phantom with GitHub's clothes — a thing that
  really happened leaving no journal — so the sweep that collects it is not optional: it reads
  each queued pull back, and a completed merge runs the *same* `factory_merge_finalize` the
  direct arm runs, so a merge by GitHub and a merge by the queue leave identical records
  (`AUTO-MERGED`, closure verification, retirement); a pull that closed unmerged is dropped
  with `AUTO-ENQUEUE-CLOSED`; an unreadable one is skipped, stamped, and fails the pass rc —
  dropping the stamp on a 404 is how a completed merge becomes an orphan tree.
  `FACTORY_AUTO_ENQUEUE=0` declines loudly (`AUTO-ENQUEUE-OFF` every pass) because a queue
  feature that quietly stops firing is the silence this harness keeps paying for. The plain
  direct merge is not deleted: the `merge_now` arm still fires when a row re-reads fully green,
  so the two arms cover the two moments — at verification, and at completion.
- Checkpoint: cf6ddb2
- Effect: `factory/factory.sh` gained `factory_auto_merge_allowed`, `factory_auto_enqueue_offer`
  (the `checks=pending` split of the `awaiting_merge` case), `factory_auto_enqueue`,
  `factory_auto_enqueue_sweep` and `factory_merge_finalize` (the direct arm's closeout tail,
  now shared), and the pass calls the sweep every activation; `factory/common.sh` gained the
  `FACTORY_AUTO_ENQUEUE` knob; `docs/factory.md` names the behaviour in the class table and the
  knob table; `factory/selftest.d/006-auto-enqueue-arm.sh` is eleven legs pinned through a fake
  `gh` that records every call. Three defects the legs measured into existence: the leg's own
  `awk -v pat="^fn\\(\\)"` had its backslashes eaten by `-v`, making `()` an empty group that
  matched the *offer*'s heading before the enqueue's — extraction now compares literal prefixes
  and fails closed when a function appears twice; `2>"$gh_err"` into an absent `$FACTORY_RUN`
  fails the merge command before gh runs, and a `mkdir` on the same command line cannot help
  because bash opens redirects before executing, so the directory is created on its own line
  and a scratch file that cannot be opened refuses the enqueue loudly; and `gh api pulls/N`
  answers `state` in uppercase — a lowercase `closed` comparison made the drop-branch dead.
  Decision: H-0411
