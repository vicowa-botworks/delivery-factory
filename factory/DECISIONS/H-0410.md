## H-0410 · For an agent installing this harness unattended, do the checks move into the installer, into the README, or into a front door over it?

- Question: an automation must be able to arm this harness against a new repository
  end-to-end and branch on the result. `install-timer.sh` is the only writer of unit files and
  is strict on purpose — `factory/install-timer.sh:307` "install-timer: refusing to install a tree that is not the trunk." is #249's guard doing its job — but everything around it is
  shaped for a person: the knobs arrive as environment, the refusal is prose meant to be read
  at a terminal, and there is no machine-readable verdict, so an agent either trusts the
  installer's last line or re-derives the machine state by hand. Measured while arming the
  harness against a fresh repository: the reviewer defaults name the harness author's own
  team, so an install that names no team asks strangers' pulls; a `gh` that works in the
  terminal is invisible to the unit unless the PATH capture sees it; and `common.sh` refuses at
  SOURCE time — `factory/common.sh:72` "is the harness itself" — which kills the standard agent
  invocation (`cd <harness> && factory/install.sh --target <new-repo>`) before a single flag is
  parsed. Where does the agent interface live without weakening the writer?
- Options: fold the checks and a `--json` mode into `install-timer.sh` itself, one script for
  human and machine — but that file is the single writer whose success prose the units'
  operators read, and parsing envelopes between rendering unit files is where a writer starts
  disagreeing with what it wrote — | documentation-only: a README section telling agents the
  four preconditions to test themselves — but that makes every integrator re-derive the checks,
  and each re-derivation is free to be wrong, which is how a timer gets "installed" and never
  fires | a separate front door, `factory/install.sh`, that adds checks and a verdict and no policy
- Chose: a separate front door, `factory/install.sh`, that adds checks and a verdict and no policy
- Why: the door carries named checks before any write, knobs as flags, a one-line `--json`
  envelope on stdout with prose on stderr, exit codes that branch, and a `--verify` that reads
  the machine back from systemd and the files, while every unit file is still written, removed
  and reloaded only by `install-timer.sh` — the two authorities stay separated. The writer stays
  byte-identical, so nothing an agent passes through it can bypass #249, the PATH capture, or
  the SuccessExitStatus rules, and the door is free to be paranoid because it owns no units. The envelope is stdout's only
  line: `log_event` echoes to stdout by design, which poisoned every `jq` parse until the front
  door's own verdict went straight to the journal file — the same lesson #1180 records for
  GitHub artifacts, re-measured one level down: an installer's last line is a claim, and
  `--verify` exists so success is always a read-back (unit files on disk, `list-timers` with an
  armed elapse, `ExecStart` loaded, `FACTORY_ROOT` pinned), never a restatement. Two `set -e`
  classes surfaced while the legs were built and are recorded here because they are the shape
  of the hazard, not one bug each: a pipeline inside `$(...)` carries `pipefail` into the
  assignment's status, so a `systemctl cat` of a missing unit killed the script before the
  envelope existed (rc 1, no reason — the worst output a machine-facing tool can produce), and
  a guarded printf inside the envelope block truncated the object mid-key. The README was
  restructured around the same finding from the human side: what an operator needs first is
  what this is and how to arm it against a new project, and the internals, layout, and roadmap
  read better after both than before them.
- Lost: the soft-`gh` arm of the leg's shim (the front door's incidental installer calls answer
  `[]` rather than asserting — the leg that asserts them is install-timer's own), and one more
  script in the layout to keep in step with the writer; leg `005-agent-front-door.sh` is the
  thing in step, driving the real front door end to end through fake `gh`/`systemctl` and
  asserting the pair lands, pins, enables, and reads back. Proof posture on the legs: 7 passed
  on the branch, the red-tree runner refuses `origin/main` at its preconditions (rc 70, the
  tree lacks the subject at all — it cannot report a pass it did not measure), and one
  mutation (undoing the target-slug carry) reddens exactly the two legs that depend on it and
  nothing else.
- Checkpoint: 19ea1f2
- Effect: `factory/install.sh` (front door: `--target/--reviewer-team/--reviewer/--interval/
  --name/--dry-run/--json/--verify/--uninstall`), `factory/selftest.d/005-agent-front-door.sh`
  (7 legs), `README.md` restructured (quick start first, internals last, agent block, no
  target-project references), and a front-door section in `docs/factory.md`.
- Decision: H-0410
